2 · Diagnostic — Bloquant 3 · tous corrigés

F1

Aucun UseForwardedHeaders derrière le proxy inverse

BloquantCorrigé
Constat
Le Volume 9 §2 décrit un déploiement Nginx (TLS) → conteneurs ASP.NET. Program.cs ne configurait pas les en-têtes transférés. Conséquence : Connection.RemoteIpAddress vaut l'IP du proxy pour toutes les requêtes, et Request.Scheme reste http.
Impact
Les limiteurs de débit partitionnés par IP — login (anti credential-stuffing), inscription publique de masse, réinitialisation de mot de passe, annuaire public — se retrouvent tous sur une partition unique. Le contrôle anti-abus soigneusement posé dans Program.cs devient inopérant en production : soit un déni de service accidentel du login pour tout le monde, soit l'IP d'un attaquant devient invisible. En prime, UseHttpsRedirection peut boucler.
Correctif — UseForwardedHeaders (XForwardedFor | XForwardedProto) posé en tout premier dans le pipeline, activé par ForwardedHeaders:Enabled=true (Staging/Prod uniquement — inerte en Development). Clés ForwardedHeaders:ForwardLimit et ForwardedHeaders:KnownProxies documentées dans .env.example. À l'équipe ops : renseigner KnownProxies si le port applicatif peut être atteint autrement que par le proxy.
F2

Aucune sonde de santé exposée

BloquantCorrigé
Constat
Rien ne répond sur /health. Or le Volume 9 §2.1, §4 (étape 10 « health check post-déploiement ») et §9 (« disponibilité de l'API (health checks) ») supposent tous une sonde — indispensable au load balancer, au rolling update et au rollback automatique.
Impact
Impossible de router du trafic uniquement vers une instance saine ; un déploiement progressif enverrait des requêtes vers un conteneur dont la base n'est pas encore joignable ; le contrôle post-déploiement de la CI (§4) n'a pas de cible.
Correctif — AddHealthChecks() + DatabaseHealthCheck (un SELECT 1, aucune table tenant). Trois endpoints anonymes, hors /api/, non soumis aux limiteurs : /health/live (le process répond, sans dépendance — pas de redémarrage en boucle si la base cligne), /health/ready (PostgreSQL joignable — sonde du rolling update), /health (agrégat).
F3

Le bootstrap des deux rôles PostgreSQL a disparu du dépôt

BloquantCorrigé
Constat
docker/postgres/init/01-create-app-role.sh — le script qui crée le rôle applicatif sama_ecole_app (NOSUPERUSER, NOBYPASSRLS) — a été supprimé au commit d8e2197 (« nettoyage des fichiers dupliqués à la racine »), en dommage collatéral. Le dossier docker/postgres/init/ est resté vide ; docker-compose.yml le monte toujours et passe toujours DB_APP_USER/DB_APP_PASSWORD que plus rien ne consomme ; la migration EnableRowLevelSecurity pointe toujours vers lui. Le .gitattributes documente la panne qui en découle (« le rôle sama_ecole_app n'était plus créé ») mais le script n'a jamais été remis.
Impact
Sur un checkout propre : docker compose down -v && up produit un PostgreSQL sans le rôle applicatif → l'application ne peut pas se connecter, ou démarre sur le rôle propriétaire et RlsGuard refuse le démarrage. L'onboarding d'un nouveau développeur est cassé, et la moitié opérationnelle de la règle #2 (création + privilèges du rôle) n'est plus versionnée nulle part.
Correctif — script recréé (fins de ligne LF garanties par .gitattributes, bit exécutable posé). Version corrigée : il crée le rôle + GRANT CONNECT + GRANT USAGE ON SCHEMA, et rien d'autre. L'ALTER DEFAULT PRIVILEGES … SELECT, INSERT, UPDATE, DELETE du script d'origine est retiré : il ré-accordait DELETE en douce sur toute table future, ce qui contredit la règle #6 (aucune suppression physique). Les GRANT par table restent la responsabilité des migrations.

3 · Diagnostic — Majeur 2 · tous corrigés

F4

AuditLoggingBehavior écrit l'audit d'échec via un DbContext déjà en échec

MajeurCorrigé
Constat
Dans son catch, le comportement faisait dbContext.AuditLogs.Add(…) puis dbContext.SaveChangesAsync() — sur le même DbContext de requête que le Handler qui vient d'échouer. Après un échec, le ChangeTracker peut encore porter des entités mises en attente (voire un SaveChanges déjà en échec).
Impact
Sur un conflit de concurrence xmin ou une violation d'unicité (précisément les cas visés par la règle #5, sur Payments / Grades / Frais), le SaveChangesAsync de l'audit relève sur les entités périmées du Handler : l'entrée success:false promise par JGK-H01 est silencieusement perdue. Risque latent aggravé : un futur Handler qui met une écriture en attente avant de lever une règle métier verrait cet état partiel committé par le SaveChanges de l'audit.
Correctif — l'écriture passe par IAuditLogStore.AppendAsync (un seul SELECT append_audit_log(…) en ADO.NET brut, fonction SECURITY DEFINER déjà utilisée pour l'audit de connexion). Aucun SaveChangesAsync : le ChangeTracker du Handler n'est jamais repartagé. Effet de bord positif : les entrées d'audit d'échec sont désormais réellement persistées.
F5

ClassroomsController.DownloadSchoolCards — ContinueWith(t => t.Result) sur un appel MediatR

MajeurCorrigé
Constat
Le repli « année active » était calculé par mediator.Send(new GetSchoolYearsQuery()).ContinueWith(t => t.Result?.FirstOrDefault(y => y.IsActive)?.Id …).
Impact
t.Result sur une tâche en faute lève une AggregateException qui n'est pas dans le switch de ExceptionHandlingMiddleware : un NOT_FOUND ou un 422 remonté par GetSchoolYearsQuery ressortirait en 500 brut au lieu du code normalisé (règle #9). De plus ContinueWith sans TaskScheduler explicite hérite d'un ordonnanceur ambigu.
Correctif — await direct de la requête, avec repli lisible sur Guid.Empty. Chemin peu fréquent, mais c'est exactement le type d'anti-pattern demandé au périmètre « méthodes trop complexes / dette technique ».

4 · Diagnostic — Mineur 6 · 2 corrigés · 4 recommandations

F6

TenantConnectionInterceptor.ConnectionOpened — sync-over-async

MineurCorrigé
Constat
Le chemin d'ouverture synchrone d'EF Core faisait ApplyTenantAsync(…).GetAwaiter().GetResult() pour poser app.current_school_id.
Impact
Bloque un thread du pool sur une E/S base à chaque ouverture de connexion synchrone : risque de famine de threads sous charge. L'application étant quasi entièrement async, le chemin est rarement emprunté — d'où la sévérité mineure.
Correctif — vraie exécution synchrone (ExecuteNonQuery) pour l'override sync ; SQL et paramétrage identiques, aucune machine à états asynchrone.
F7

En-têtes de durcissement manquants

MineurCorrigé
Constat
SecurityHeadersMiddleware posait nosniff, X-Frame-Options, X-XSS-Protection et une CSP stricte, mais pas de Referrer-Policy ni de Permissions-Policy.
Impact
Fuite du Referer complet vers les hôtes d'images externes (logo d'établissement) ; aucune restriction sur les API navigateur puissantes (caméra, géoloc, paiement) qu'un script injecté pourrait tenter d'exploiter.
Correctif — Referrer-Policy: strict-origin-when-cross-origin + Permissions-Policy qui neutralise caméra / micro / géoloc / paiement / USB / MIDI… (l'app n'en utilise aucune — saisie GPS au clavier, QR lu par l'appareil photo natif). Assertions ajoutées à SecurityHeadersTests.
F8

AllowedHosts: "*" non restreint pour la production

MineurRecommandation
Constat
appsettings.json garde AllowedHosts: "*" ; appsettings.Production.json ne le surcharge pas.
Impact
Défense en profondeur uniquement — Nginx valide déjà l'en-tête Host. Sans proxy correctement configuré, ouvre la porte à des attaques par Host header (empoisonnement de cache, liens absolus).
Reco
Poser le(s) domaine(s) réel(s) via AllowedHosts dans appsettings.Production.json ou une variable d'environnement.
F9

Webhooks publics sans limiteur de débit

MineurRecommandation
Constat
POST /webhooks/payments/{provider} et POST /webhooks/sms/{provider} sont [AllowAnonymous] (voulu — l'agrégateur appelle sans JWT) mais ne portent aucune [EnableRateLimiting].
Impact
La vérification de signature est peu coûteuse, donc le risque de DoS est modéré, mais un endpoint public non authentifié sans plafond reste une exposition inutile.
Reco
Ajouter une politique de débit par IP, généreuse (les agrégateurs rejouent légitimement), sur ces deux routes.
F10

SubscriptionAwaitingPaymentMiddleware — un aller-retour BDD par requête /api/*

MineurDifférable
Constat
Chaque requête API interroge subscriptions pour lire le statut de l'école. Compromis documenté (le JWT ne porte volontairement aucun claim d'abonnement).
Impact
Performance uniquement : une lecture indexée supplémentaire sur le chemin chaud.
Reco
Cache par école à TTL court (quelques secondes), invalidé au traitement du webhook de confirmation. Non bloquant — à traiter si la latence P99 le justifie.
F11

X-XSS-Protection: 1; mode=block — en-tête hérité

MineurÀ arbitrer
Constat
Le ticket JGK-F01 impose 1; mode=block. L'OWASP recommande aujourd'hui 0 (l'auditeur XSS des anciens navigateurs a lui-même été une source de vulnérabilités type XS-Leaks).
Impact
Faible dans les deux sens. La CSP script-src sans unsafe-inline est la vraie protection.
Reco
Décision produit : conserver (conformité au ticket) ou passer à 0 (aligné pratiques actuelles). Laissé tel quel dans cette passe.

I2

Vérifier les GRANT effectifs de sama_ecole_app sur la base réelle

Info
Constat
La migration EnableRowLevelSecurity émet un GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES global pour les tables existant à ce point ; les migrations suivantes accordent SELECT, INSERT, UPDATE (sans DELETE) par table, avec DELETE explicite sur quelques tables de liaison seulement.
Reco
Sur la base de Staging, contrôler (\dp) que le jeu de privilèges effectif du rôle applicatif correspond bien au modèle voulu : SELECT/INSERT/UPDATE partout, DELETE uniquement sur la liste blanche (teacher_subjects, refresh_tokens, classrooms, paie, décaissements…).
I3

Couverture RLS — s'appuyer sur RlsCoverageTests en CI

Info
Constat
RlsGuard vérifie au démarrage que le rôle applicatif ne contourne pas la RLS et ne possède aucune table — mais pas que chaque table tenant a bien ROW LEVEL SECURITY activé + une policy. C'est RlsCoverageTests (catégorie MultiTenant) qui le fait, table par table.
Reco
Confirmer que la CI exécute dotnet test --filter Category=MultiTenant et bloque le déploiement à son échec (Volume 9 §4 étape 2 le prévoit déjà — vérifier l'implémentation du pipeline).
I4

Chaîne de connexion Supabase — deux rôles obligatoires

Info
Constat

Reco
Rien à coder — RlsGuard refuse le démarrage si l'application tourne sur un rôle propriétaire / superutilisateur / BYPASSRLS. À valider au premier démarrage Staging : le guard doit passer.
